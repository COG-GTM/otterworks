# Runtime-testing the Capacitor Android app

Covers `frontend/client-app` and its `mobile/android` Capacitor project. Use this when you must
prove the Android app actually **builds and runs**, not just that files changed. (For the
standalone Maven/Spring services see `jvm-service-runtime-testing` — a different domain.)

## Pin the JDK and SDK explicitly — the shell default is often wrong

`JAVA_HOME` is written to `$ENVRC` by the blueprint, which only affects *later* sessions. In the
session that built the snapshot — and often in yours — the shell default can still be a different
JDK than the project targets. Always pin per command:

```bash
export JAVA_HOME=/usr/lib/jvm/java-17-openjdk-amd64   # match the Capacitor major version
export ANDROID_HOME=$HOME/Android/Sdk
export PATH=$ANDROID_HOME/platform-tools:$ANDROID_HOME/emulator:$PATH
export NVM_DIR="$HOME/.nvm"; . "$NVM_DIR/nvm.sh"; nvm use default   # system node may be too old for Vite
```

**The Capacitor major version dictates the JDK**: `@capacitor/android`'s own
`capacitor/build.gradle` hardcodes `sourceCompatibility`/`targetCompatibility`. Capacitor 6 → 17,
Capacitor 7/8 → 21. You can check any version without installing it:

```bash
cd /tmp && npm pack @capacitor/android@<version> && tar xzf capacitor-android-*.tgz
grep -n "Compatibility" package/capacitor/build.gradle
```

Full build loop:
```bash
cd frontend/client-app
npm ci && npm run build && npx cap sync android
cd mobile/android && ./gradlew --no-daemon assembleDebug
```

## `capacitor.build.gradle` is generated — always re-check it after `cap sync`

`mobile/android/app/capacitor.build.gradle` is regenerated by `npx cap sync android` but is
**tracked in git**. Any hand-edit to its `compileOptions` can be silently reverted. The cheap,
decisive assertion is a git diff rather than eyeballing the file:

```bash
npx cap sync android
git diff --exit-code -- frontend/client-app/mobile/android/app/capacitor.build.gradle  # want 0
grep -rn "VERSION_21\|VERSION_17" mobile/android --exclude-dir=build --exclude-dir=.gradle
```

## Prove *which* JDK compiled the code — a green build is not enough

Gradle can succeed for reasons unrelated to the JDK you think you pinned. Two hard checks:

1. **Class-file major version** of the compiled Capacitor library (61 = Java 17, 65 = Java 21):
   ```bash
   f=$(find node_modules/@capacitor/android -path "*intermediates/javac*" -name "*.class" | head -1)
   od -An -tu1 -N8 "$f" | awk '{print $8}'
   ```
2. **Negative control** — temporarily bump `capacitor.build.gradle` to the *next* Java version and
   confirm the same build now fails with `error: invalid source release: NN`, then restore it and
   assert `git diff --exit-code`. If it still passes, your JDK pin isn't doing anything.

APK metadata (use a build-tools version >= compileSdk):
```bash
$ANDROID_HOME/build-tools/<ver>/aapt2 dump badging app/build/outputs/apk/debug/app-debug.apk \
  | grep -E "^package:|^minSdkVersion|^targetSdkVersion"
adb shell dumpsys package com.otterworks.app | grep -E "minSdk|targetSdk"
```

## Emulator: build against a new API, run on an older image

`minSdk` is low (24), so an APK compiled against a newer `compileSdk`/`targetSdk` runs fine on an
older system image. This matters because **system images newer than API 36 have not booted on this
microVM**: SurfaceFlinger crash-loops with
`Assertion failed: !rcEnc->featureInfo()->hasReadColorBufferDma` under every software renderer
(`swiftshader_indirect`, `swangle_indirect`, `-gpu guest`) as soon as an app window appears. Keep
the AVD on `system-images;android-36;google_apis;x86_64` and don't burn time fighting this. Never
claim runtime coverage for the newer API level — say the APK was *built* against it and *run* on 36.

## Getting a recordable emulator window

The blueprint starts the emulator with `-no-window`, which is useless for a screen recording.

- **Do not rely on `scrcpy` from apt.** Ubuntu 22.04 ships scrcpy 1.21, which cannot mirror
  Android 13+ — it dies with `NoSuchMethodException: android.view.SurfaceControl.createDisplay`.
  A scrcpy >= 2.x built from source might work, but restarting the emulator is simpler.
- Restart it **with** a window (drop `-no-window`), then size it for the recording:
  ```bash
  adb emu kill; sleep 5
  setsid nohup $ANDROID_HOME/emulator/emulator -avd otter -no-audio -no-snapshot \
      -gpu swiftshader_indirect > /tmp/emu.log 2>&1 < /dev/null & disown
  # boot takes ~3-5 min:
  until [ "$(adb shell getprop sys.boot_completed 2>/dev/null | tr -d '\r')" = 1 ]; do sleep 10; done
  DISPLAY=:0 wmctrl -r "Android Emulator - otter:5554" -e 0,560,0,480,1150
  ```
  Use `setsid ... & disown`; a plain backgrounded `nohup` inside a short-lived exec shell can be
  killed with the shell before it detaches.
- Dismiss the "Emulator Running in Nested Virtualization" dialog before recording.

## Typing into the app

`xdotool type` (the computer-use `type` action) frequently does **not** reach WebView inputs and
may pop Gboard's "Try out your stylus" onboarding dialog. Use adb instead — the text still appears
on screen, so it records fine:

```bash
adb shell input text "QA%sCapacitor6"   # %s = space
adb shell input keyevent 111            # ESC / dismiss keyboard
```
Tap the field first, and use the IME's "next field" key to reach inputs hidden behind the keyboard.

## Reaching the backend from the device

Native builds do **not** use a relative `/api/v1`; `src/lib/api-client.ts` sends them to
`http://10.0.2.2:8080/api/v1` (`10.0.2.2` = the emulator's alias for the host loopback). So bring
the backend up on the host first with `make up` (~22 containers; check
`curl localhost:8080/health`). Cleartext to `10.0.2.2` is allowed only in **debug** builds via
`mobile/android/app/src/debug/res/xml/network_security_config.xml`.

**This makes any in-app login/registration a genuine test of the Capacitor bridge.** The app's only
Capacitor API is `Capacitor.isNativePlatform()`. If the native bridge fails to inject, that returns
`false`, the base URL silently falls back to relative `/api/v1` against the `https://localhost`
WebView origin, and every request fails. A successful sign-in therefore proves the bridge is live —
a much stronger signal than "the landing page rendered".

### Credentials

`DRIVE_EMAIL` / `DRIVE_PASSWORD` (the seeded RetailCo drive account) are **not** always present in
the session environment, and a freshly rebuilt stack may have no seeded drive at all. Rather than
blocking, **register a new account through the app UI** — it is itself a golden-path test. The
gateway requires `{email, password, displayName}`:

```bash
curl -X POST http://localhost:8080/api/v1/auth/register -H 'Content-Type: application/json' \
  -d '{"email":"qa@example.com","password":"Passw0rd!","displayName":"QA"}'
```
A brand-new account has an empty drive, so prove the drive works by tapping **New folder** and
confirming the folder appears — a write→read round-trip that exercises the JWT interceptor too.
Re-check it after `adb shell am force-stop` + a fresh sign-in to prove server-side persistence.

## Useful runtime checks

```bash
adb logcat -c   # before launching
adb shell am start -n com.otterworks.app/.MainActivity
adb logcat -d | grep -iE "FATAL EXCEPTION|E/Capacitor|ERR_CLEARTEXT|net::ERR"   # want zero
adb logcat -d | grep "D Capacitor"   # bridge startup + which JS asset was served
```
The `Handling local request: https://localhost/assets/index-<hash>.js` line confirms the device is
running **your** build — match the hash against `dist/assets/`.

## Devin Secrets Needed

- `DRIVE_EMAIL`, `DRIVE_PASSWORD` — only if you must sign in as the pre-seeded RetailCo drive
  account. Not required: register a fresh account in-app instead (see above).
